# Guides: recipes for an agent, inside the app

Owner, 2026-11-01 (translated from Russian): "I'd add a Guides section to the menu with examples of how to do useful
things with the different CLIs. Part can be written here, part pulled from the docs on the website (we can fetch the
md via an API, or make a JSON of the docs if that's easy to support), and give links to the full docs on the site. The
idea: the user can easily see how to do great things with the tools by typing prompts for agents, and the agent calls
several commands. Like a set of recipes. Especially useful in onboarding: show that after installing they can go to
Guides and start working there."

This round is the plan and a clickable prototype. Nothing ships in the app or on the site yet.

## Why

After setup, the app shows tools with green lamps and stops. The owner's users still have to guess what to ask an
agent. The site already answers that, in recipe pages, but the app never points there. A Guides page closes the gap:
each guide is one request to paste into an agent, the tools it needs, and what the agent will run. The setup's last
step sends the user there, so the first thing they do after installing is something useful.

## Data source: decision and trade-offs

The app cannot fetch from the webview: its content security policy allows only `ipc:` (`src-tauri/tauri.conf.json:27`).
Any network read goes through a Rust command, like the bug report's (`report.rs`, `ureq`).

The options weighed in the first round:

| Option | What it takes | Good | Bad |
| --- | --- | --- | --- |
| A. `guides.json` from cli-docs, bundled snapshot in the app | Guide data in a TS module, a JSON route, a test | One place to write guides; no app release for new ones | A data file nobody reads on the site; two formats to keep |
| B. Written only in the app (`catalog/guides.json`) | The page and the data in this repo | Smallest first step; no network | New guides wait for an app release; the site and the app drift apart |
| C. Parse the site's existing recipe Markdown | Fetch `llms.mdx` pages, find headings and prompt blocks | Reuses what exists | The format is not uniform (tg has no prompt blocks); no list of needed tools or steps |

**Decision (owner, 2026-11-01): Markdown guide pages on the site, fetched by the app. No JSON.** Each guide is one
docs page in cli-docs with a fixed shape. The site shows them as a Guides section, and serves each page and an index as
raw Markdown, as it already does for `llms.txt` and `llms.mdx`. The app fetches that Markdown through Rust, parses the
fixed shape, and ships a bundled copy for offline. A cli-docs test fails the build when a guide breaks the shape or
names a command that does not exist, so the app's parser never meets a page it cannot read.

### The shape of a guide page

One file per guide and language: `content/docs/guides/<id>.md` (en), `content/docs/ru/guides/<id>.md`,
`content/docs/es/guides/<id>.md`.

```md
---
id: requests-to-tasks
title: Turn requests in your chats into tasks
outcome: Everything people asked you to do this week, as tasks you choose.
goal: plan            # catch-up | prepare | remember | plan
needs:
  all: [memo]         # every one is needed
  any: [tg, max, wa]  # one is enough
  extra: []           # used when installed
saves: true           # the agent records something; the prompt says "show first, save after I agree"
---

## Prompt

Use tg CLI and memo CLI. Find messages from the last week where someone asked me to do something. …

## Steps

1. Reads the week's conversations, yours too — `tg review date>7d`
2. Adds a task for each request you pick — `memo tasks add msg:telegram/…`

## Result

A list of requests to pick from, then tasks that link back to each message.
```

- Section headings are translated on the page (`## Запрос`, `## Шаги`, `## Результат`; `## Petición`, `## Pasos`,
  `## Resultado`), so the parser reads the sections by position (exactly three `##` sections, in this order), never by
  heading text.
- Each step is one numbered line: the sentence, an em dash, one inline code span. `run` is display text; the app
  never runs it (rule 2); the agent does.
- Tool ids are the catalog's (`catalog/tools.json`). An id the app does not know hides the guide.
- The prompt is written for Telegram (`tg CLI`). The app swaps in the messenger the user has (`wa CLI`, `max CLI`),
  like the site's `{cli}` slot.
- The "Full guide" link is the page itself, in the reader's language: no separate `docs` field, and no anchor that
  differs by language.

### Serving and fetching

- **Site**: a Guides section in the sidebar from these pages. The existing `llms.mdx` route already serves any page as
  raw Markdown (`/llms.mdx/docs/guides/<id>/content.md`, `/llms.mdx/docs/ru/guides/<id>/content.md`). One new route,
  `/llms.mdx/docs/guides/index.md` (or a `guides` block in `llms.txt`), lists the ids and their `goal` in order, so the
  app needs one request for the list and one per changed page.
- **App, first release**: `catalog/guides/<lang>/<id>.md`, copied from the site by `bin/sync-guides` before a
  release, parsed at build time into the bundled copy. The parser lives in `src/domain/guides.ts`, with the same
  rules as the cli-docs test, and a test that every bundled page parses.
- **App, later**: `src-tauri/src/guides.rs` with `guides_fetch(lang)`: the index, then each page whose ETag changed
  (fixed host `https://wirecat.dev`, `WIRECAT_DOCS_URL` overrides it for tests, 5 s timeout, 64 KB cap per page),
  cached in the app data folder. A page that does not parse is skipped and the bundled one stays. The page renders the
  bundled or cached copy at once, never waits for the network, never shows a spinner. At most one fetch a day; a
  newer copy is used the next time the page opens, never while the user reads it (rule 9). Offline, or on any error,
  the status line says "The guides that came with WireCat"; nothing else changes.

### Second design (2026-11-01)

The owner, on the first prototype: "Guides looks like Tools — it must have a different design, because it is a
different page." The first one was a rack: lamp, tool icons, title, and a "Get Memo" button per row, the same row
grammar as Tools. It put the tools first, when the point of a guide is the request and what comes back.

The second design treats the page as a recipe book of requests:

- **Start here.** Under the title, one guide is already open: the first one the owner's tools can run, in the order
  catch-up, plan the day, find a decision, prepare a call, Drive brief, call follow-ups. With `?state=one` (only
  Telegram) that is "Catch up on what you missed". Arriving from setup, its heading becomes "Your tools are ready.
  Start with this one." It is chosen once, when the tools have answered, and stays for the visit.
- **Grouped by what the owner wants done**, not by tool: Catch up, Prepare, Remember, Plan. Each group is a heading,
  one line, and a grid of cards (two columns from 40rem of page width, three from 62rem).
- **A card is a request, not a tool row**: the title, the request itself in a chat bubble (three lines, without the
  "Use tg CLI." the agent needs), and one quiet line: a green lamp and "Ready to try", or a hollow lamp and "Needs
  Zoom and memory". No button on the card; the whole card opens the guide.
- **An open guide reads as a conversation**, under its group, full width: left, "You ask your agent" with the request
  in an editable bubble, "Copy request", "Which agents are ready", where to paste it, and for guides that save, that
  the agent asks first. Right, "Your agent runs" as a small timeline (a plain sentence over the command in mono),
  "And answers with" in a reply bubble, then what it uses and the full guide on wirecat.dev.
- **Tools are secondary.** A missing tool is one line at the foot of the open guide, "Needs Google Drive", with a text
  link "Get Google Drive" (or "Turn on memory", "Get a messenger") to that tool's row on Tools. The page never says
  "Get Memo": memory is what the owner gets.
- **One purple button at a time.** "Copy request" is primary in the open guide when its tools are ready. The Start
  here guide's Copy turns outlined while another guide is open. It is outlined in a guide that is not ready, where the
  purple is the text link that installs.
- **Nothing jumps.** A card's guide opens under its group with `Collapse`; the clicked card is held in place
  (`holdInPlace`) while a guide in another group closes. Switching between cards of one group crossfades the open
  guide (`Crossfade` in `AutoHeight`). Escape or the close button folds it and returns focus to its card. `?guide=<id>`
  opens that guide and brings its group's heading to the top.
- **Before the tools answer** (first start, or the mock's first seconds) cards say "Checking your tools…" with a hollow
  lamp, and the open guide's Copy is outlined. The first prototype showed "Ready to try 0" and "Get Memo" on every row
  until the tools answered: a false statement for about 8 s in the mock. In the real app the last answer is restored
  from `localStorage` at start, so it shows only on the very first start.
- **The All / Ready filter is gone.** Readiness is on every card, and ten cards in four groups scan without one.
  `?guides=ready` no longer exists.

Directions considered and rejected (screenshots in `v2/rejected-*`):

- **A reader: guide list on the left, one guide on the right** (`rejected-reader-light.png`). Clear, but it is the
  Agents page's layout, the one list-beside-pane exception DESIGN.md allows; two pages would look alike again.
- **A feed: every guide open, one after another** (`rejected-feed-dark.png`). Shows the most, but ten full
  conversations are about nine screens; nothing can be compared at a glance.

DESIGN.md says "Don't turn the rack into a card grid". Guides are not machine things in a rack, and the owner asked
for a page that does not look like one; the cards stay flat (hairline border, no shadow) and the exception should be
written into DESIGN.md beside the Agents one if this design is accepted.

Unchanged from the first design: the sidebar entry ("Guides" after Agents, `BookOpenText`), the title row with the
status line and "All guides on wirecat.dev", the editable request, the account note (rule 3), and prompts that name the
CLI because the agent needs it while titles and outcomes say what the user gets.

Mock scenarios (prototype): `?section=guides`, `?guides=first`, `?guides=offline`, `?guide=<id>`, combined with
`?state=one` (only Telegram) or `?state=mixed` (all but Drive).

## The guides (10)

Every command was checked against the live command pages on wirecat.dev (`/llms.mdx/docs/<tool>/commands…`,
2026-11-01), including the `wa` and `max` forms the app makes from a `tg` prompt: `inbox`, `review`, `messages list`,
`contacts context`, `chats documents list`, `attachments download`, `attachments extract` and `search messages` exist
for all three messengers. Every "Full guide" anchor was checked in en, ru and es. Names, chats and projects are made
up.

| Guide | Needs | What the agent runs |
| --- | --- | --- |
| Catch up on what you missed | a messenger | `tg inbox date>18h`, `tg review date>18h` |
| Prepare for a call with someone | Memo (+ Zoom) | `memo context`, `zm meetings context`, `memo tasks list` |
| Turn requests in your chats into tasks | Memo + a messenger | `tg review date>7d`, `memo tasks add` |
| Find a file someone sent and keep what matters | Memo + a messenger | `tg chats documents list`, `tg attachments download`, `tg attachments extract`, `memo facts add` |
| Turn a Zoom call into follow-ups | Zoom + Memo | `zm meetings list`, `zm meetings summary`, `zm meetings task-proposal`, `memo tasks add` |
| Find where something was decided | Memo | `memo search all`, `memo search mail` |
| Plan your day | Memo | `memo tasks agenda`, `memo reminders list` |
| Check your promises before you reply | a messenger | `tg contacts context`, `tg messages list` |
| Brief yourself on a project from Drive | Google Drive | `drive sync`, `drive search`, `drive documents context` |
| Remember what someone prefers | Memo + a messenger | `memo search messages`, `memo memories add` |

Four of them save something (tasks, facts, a memory); their prompts ask the agent to show first. The two memo pages
disagree on what happens next: the command reference says an agent's fact or memory "waits as proposed until you
confirm it", the memo recipes page says one added with the command "is confirmed at once". So the page promises only
what the prompt asks for (show first, save after you agree), not what memo does afterwards.

Drive's docs do not say it writes to the shared archive, so no guide mixes Drive with memo search.

## Decisions (owner, 2026-11-01)

- **NEED-A · The section's name**: **A**, "Guides" / "Рецепты" / "Guías".
- **NEED-B · Where the guides are written**: the owner's own variant. Markdown pages in cli-docs, shown on the site,
  fetched by the app; no JSON (see "Data source").
- **NEED-C · The last setup step**: **B**. "Try your first guide" is the main (purple) button; "Open Tools" is a
  secondary one beside it. Wired on the review branch.

### NEED-D · Should a guide start the agent itself, or only copy the request?

- Now: the prototype copies the request; the user pastes it into an agent.
- Options: **A** copy only · **B** also "Open in Claude Code" (and other agents with a command line), which opens a
  terminal with the agent and the request, through `terminal.rs` with a fixed program and the request as one
  argument.
- Pick: **A** now, B as a follow-up. B needs a per-agent launch command and a safe way to pass free text (rule 2);
  copy works for every agent today, including ChatGPT in a browser.
- If no answer: A ships; B stays in the backlog.

## Not verified

- The query words in `run` beyond those the reference shows (`date>18h`, `date>7d` follow the documented `date>2h`).
- That a prompt run by a real agent calls exactly these commands. The steps say what it usually runs; agents vary.
  No CLI was run against a real account.
- How the page reads with 30+ guides. Beyond about 15, a filter by tool may be needed.
- The prototype's animations (a guide opening, the crossfade between two guides of one group, the clicked card held
  in place): the screenshots run with reduced motion, so none of them shows an animation.
