# Guides: recipes for an agent, inside the app

Owner, 2026-11-01 (translated from Russian): "I'd add a Guides section to the menu with examples of how to do useful
things with the different CLIs. Part can be written here, part pulled from the docs on the website (we can fetch the
md via an API, or make a JSON of the docs if that's easy to support), and give links to the full docs on the site. The
idea: the user can easily see how to do great things with the tools by typing prompts for agents, and the agent calls
several commands. Like a set of recipes. Especially useful in onboarding: show that after installing they can go to
Guides and start working there."

This round is the plan and a clickable prototype. Nothing ships in the app or on the site yet.

## Why

After setup, the app shows tools with green lamps and stops. The owner's users still have to guess what to ask an
agent. The site already answers that, in recipe pages, but the app never points there. A Guides page closes the gap:
each guide is one request to paste into an agent, the tools it needs, and what the agent will run. The setup's last
step sends the user there, so the first thing they do after installing is something useful.

## What the docs site has today

9d6573cb a few minutes later) and the live site. The local checkout
`/home/leemour/Projects/AI/cli-docs` is on an older branch; nothing here comes from it.

  Pages by `.github/workflows/deploy.yml` (`next build`, then `wrangler pages deploy out`). It rebuilds on a push to
  main, daily, and on a `repository_dispatch` from the tool repos.

- **Recipe pages exist** for tg, max, wa, memo and drive (`/en/docs/<tool>/recipes`), in en, ru and es. Each section is
  a heading, a prompt, and a paragraph that names the commands. The format is not uniform: memo and drive put the

- **Structured guide data already exists for tg, max and wa**: `lib/reader-guides.ts` and `lib/role-guides.ts` hold
  tuples of id, title, prompt with a `{cli}` slot, expected result, docs page and link label, in three languages. They
  render the "usage", "rankings", "bot" and "groups" pages. This is the closest thing to what the app needs.
- **Machine-readable output that is live now** (checked with `curl`, 2026-11-01):
  - `https://wirecat.dev/llms.txt` — an index with absolute links to each page's Markdown (`app/llms.txt/route.ts`).
  - `https://wirecat.dev/llms.mdx/docs/<tool>/recipes/content.md` and `/llms.mdx/docs/ru/...` — raw Markdown per page,
    in each language (`app/llms.mdx/docs/[[...slug]]/route.ts`). Headings carry their anchor: `## Morning summary
    [#morning-summary]`.
  - `https://wirecat.dev/api/search/<lang>` — the static search index.
  - No `guides.json` (404). No cross-tool recipe page.
- **The cheapest way to publish JSON** is a route like `app/llms.txt/route.ts`: `export const revalidate = false` and a
  `GET` that returns `Response.json(...)`. The static export writes it to `out/guides.json`, with no new build step
  and no change to the workflow.

## Data source: decision and trade-offs

The app cannot fetch from the webview: its content security policy allows only `ipc:` (`src-tauri/tauri.conf.json:27`).
Any network read goes through a Rust command, like the bug report's (`report.rs`, `ureq`).

| Option | What it takes | Good | Bad |
| --- | --- | --- | --- |
| **A. `guides.json` from cli-docs, bundled snapshot in the app** (recommended) | Guide data in cli-docs (a TS module like `reader-guides.ts`), a `guides.json` route, a test; the app bundles a copy and, later, refreshes it | One place to write guides; the site can show the same ones; new guides reach installed apps without a release; offline works | Two repos change; the app needs a Rust fetch and a cache for the refresh |
| B. Written only in the app (`catalog/guides.json`) | The page and the data in this repo | Smallest first step; no network | New guides wait for an app release; the site and the app drift apart |
| C. Parse the site's recipe Markdown | Fetch `llms.mdx` pages, find headings and prompt blocks | Reuses what exists | The format is not uniform (tg has no prompt blocks); no list of needed tools or steps; any page edit can break the parser |

**Recommendation: A, in two steps.** First, the guides live in cli-docs and a static `guides.json` is published; the
app bundles a snapshot taken at build time and never touches the network. Second, the app refreshes that snapshot in
the background. Cross-tool guides have no other home (per-tool recipes belong to the tool repos), and a cli-docs test
can check every command a guide shows against the synced command pages, so a renamed command fails the docs build
instead of misleading a user.

### The refresh (step 2)

- `src-tauri/src/guides.rs`: `guides_fetch()` reads one fixed URL, `https://wirecat.dev/guides.json`
  (`WIRECAT_DOCS_URL` overrides it for tests), 5 s timeout, 512 KB cap, `If-None-Match` with the cached ETag.
- The answer is cached in the app data folder (`guides.json` plus its ETag) and validated with valibot in `platform`.
- The page renders the bundled or cached copy at once. It never waits for the network and never shows a spinner.
- At most one fetch a day. A newer copy is used the next time the page opens, never while the user reads it (rule 9).
- `schema` is a number. A copy with a schema the app does not know is ignored, and the bundled copy stays.
- Offline, or on any error: the status line says "The guides that came with WireCat"; nothing else changes.

### The shape of a guide

As in the prototype (`.impeccable/mocks/guides/prototype/guides.ts`):

```json
{
  "schema": 1,
  "guides": [
    {
      "id": "requests-to-tasks",
      "needs": { "all": ["memo"], "any": ["tg", "max", "wa"], "extra": [] },
      "title": { "en": "Turn requests in your chats into tasks", "ru": "…", "es": "…" },
      "outcome": { "en": "Everything people asked you to do this week, as tasks you choose.", "ru": "…", "es": "…" },
      "prompt": { "en": "Use tg CLI and memo CLI. Find messages from the last week …", "ru": "…", "es": "…" },
      "steps": [{ "text": { "en": "Reads the week's conversations, yours too" }, "run": "tg review date>7d" }],
      "result": { "en": "A list of requests to pick from, then tasks that link back to each message." },
      "saves": true,
      "docs": {
        "en": "https://wirecat.dev/en/docs/memo/recipes#turn-requests-into-tasks",
        "ru": "https://wirecat.dev/ru/docs/memo/recipes#превратить-просьбы-в-задачи",
        "es": "https://wirecat.dev/es/docs/memo/recipes#convertir-peticiones-en-tareas"
      }
    }
  ]
}
```

- `needs.all`: every one is needed. `needs.any`: one is enough (a messenger). `needs.extra`: used when installed.
- Tool ids are the catalog's (`catalog/tools.json`). An id the app does not know hides the guide.
- `run` is display text. The app never runs it (rule 2); the agent does.
- `docs` is one full URL per language: the site translates its headings, so a recipe's anchor differs by language
  (`#turn-requests-into-tasks`, `#превратить-просьбы-в-задачи`). Replacing `/en/` in one URL would land on the top
  of the page.
- `saves: true` means the agent records something. Its prompt must say "show me first, save after I agree", as the
  site's recipes do; the page says so beside the prompt.
- The prompt is written for Telegram (`tg CLI`). The app swaps in the messenger the user has (`wa CLI`, `max CLI`),
  like the site's `{cli}` slot.

## The page

Prototype: `.impeccable/mocks/guides/prototype/GuidesPage.tsx`, on the app's own components and the real tool store.

- **Sidebar**: "Guides" after Agents, before the sections that are not built yet. The icon is `BookOpenText`.
- **Title row**: "Guides", a status in `ink-dim` ("Up to date with wirecat.dev" or the offline line), and "All guides
  on wirecat.dev" on the right.
- **One rack, one row per guide** (DESIGN.md: no card grid). A row has a lamp (green when every tool it needs is
  installed, hollow when not), the icons of the tools it uses, the title and a one-line outcome, and one action:
  - ready: **Copy request** (secondary; the One Purple Action Rule keeps purple for installs);
  - not ready: **Get Zoom** (or "Get a messenger"), which opens that tool's row on Tools, where Install is.
- **Filter**: "All 10" and "Ready to try 9". Rows that leave fold away with `Collapse`; nothing jumps.
- **The panel under a row** (`Collapse`, `holdInPlace` on the row), two columns from `lg`:
  - left: the request in an editable box ("Change the names and dates to yours before you copy"), Copy request,
    "Which agents are ready" (opens Agents), where to paste it, and for `saves` guides "Your agent shows you what it
    would save and saves only after you agree";
  - right: "What your agent runs", numbered steps, each a plain sentence over the command in mono (not a copy field:
    the user does not run these); "If you have more than one account, your agent asks which one to use" (rule 3);
    "What you get"; "Needs" with a lamp and Install per tool; "Full guide on wirecat.dev", opened in the browser.
- **Arriving from setup**: the last setup step gets "Try your first guide". The page then opens on "Ready to try"
  with a short note in place of the intro: "Your tools are ready. Try one of these first."
- **Text**: titles and outcomes describe what the user gets and say WireCat, never a CLI as the product. Tool names
  appear where the user picks tools ("Needs: Telegram"). Prompts name the CLI, because the agent needs it.

Mock scenarios (prototype): `?section=guides`, `?guides=first`, `?guides=offline`, `?guides=ready`, `?guide=<id>`,
combined with `?state=one` (only Telegram) or `?state=mixed` (all but Drive).

## The guides (10)

Every command was checked against the live command pages on wirecat.dev (`/llms.mdx/docs/<tool>/commands…`,
2026-11-01), including the `wa` and `max` forms the app makes from a `tg` prompt: `inbox`, `review`, `messages list`,
`contacts context`, `chats documents list`, `attachments download`, `attachments extract` and `search messages` exist
for all three messengers. Every "Full guide" anchor was checked in en, ru and es. Names, chats and projects are made
up.

| Guide | Needs | What the agent runs |
| --- | --- | --- |
| Catch up on what you missed | a messenger | `tg inbox date>18h`, `tg review date>18h` |
| Prepare for a call with someone | Memo (+ Zoom) | `memo context`, `zm meetings context`, `memo tasks list` |
| Turn requests in your chats into tasks | Memo + a messenger | `tg review date>7d`, `memo tasks add` |
| Find a file someone sent and keep what matters | Memo + a messenger | `tg chats documents list`, `tg attachments download`, `tg attachments extract`, `memo facts add` |
| Turn a Zoom call into follow-ups | Zoom + Memo | `zm meetings list`, `zm meetings summary`, `zm meetings task-proposal`, `memo tasks add` |
| Find where something was decided | Memo | `memo search all`, `memo search mail` |
| Plan your day | Memo | `memo tasks agenda`, `memo reminders list` |
| Check your promises before you reply | a messenger | `tg contacts context`, `tg messages list` |
| Brief yourself on a project from Drive | Google Drive | `drive sync`, `drive search`, `drive documents context` |
| Remember what someone prefers | Memo + a messenger | `memo search messages`, `memo memories add` |

Four of them save something (tasks, facts, a memory); their prompts ask the agent to show first. The two memo pages
disagree on what happens next: the command reference says an agent's fact or memory "waits as proposed until you
confirm it", the memo recipes page says one added with the command "is confirmed at once". So the page promises only
what the prompt asks for (show first, save after you agree), not what memo does afterwards.

Drive's docs do not say it writes to the shared archive, so no guide mixes Drive with memo search.

## Open decisions for the owner

### NEED-A · What is the section called in each language?

- Now: the prototype says "Guides" (en), "Рецепты" (ru), "Guías" (es). The site's per-tool pages are called
  "Recipes", "Рецепты", "Recetas".
- Options: **A** "Guides" / "Рецепты" / "Guías" (as the prototype) · **B** "Recipes" / "Рецепты" / "Recetas" (the
  same word as the site's pages) · **C** "Guides" / "Гайды" / "Guías".
- Pick: **A**. "Guides" is the owner's word, and "Рецепты" reads more naturally in Russian than "Гайды".
- If no answer: A ships, and the word in English and Spanish differs from the site's "Recipes" pages.

### NEED-B · Where are the guides written and kept?

- Now: no cross-tool guides exist anywhere; per-tool recipes live in each tool repo; the site publishes no JSON.
- Options: **A** in cli-docs, published as `guides.json`, bundled in the app, refreshed later · **B** only in the
  app (`catalog/guides.json`), with links to the site · **C** the app parses the site's recipe Markdown.
- Pick: **A**. One place to write them, a docs test catches a renamed command, and new guides reach users without an
  app release.
- If no answer: the desktop page can still be built on a bundled file, but the cli-docs work does not start, and the
  file's content must later move.

### NEED-C · What does the last setup step offer first?

- Now: the step "You are set up" has "Open Tools" as its main button and, in the prototype, "Try your first guide" as
  a smaller one beside "See which agents use them".
- Options: **A** keep "Open Tools" as the main button, guides as a smaller one (prototype) · **B** make "Try your
  first guide" the main button, Tools a smaller one.
- Pick: **B**. The owner's goal for setup is "start working", and the guides are where work starts; Tools is one
  click away in the sidebar.
- If no answer: A ships; the link to guides is there but easy to miss.

### NEED-D · Should a guide start the agent itself, or only copy the request?

- Now: the prototype copies the request; the user pastes it into an agent.
- Options: **A** copy only · **B** also "Open in Claude Code" (and other agents with a command line), which opens a
  terminal with the agent and the request, through `terminal.rs` with a fixed program and the request as one
  argument.
- Pick: **A** now, B as a follow-up. B needs a per-agent launch command and a safe way to pass free text (rule 2);
  copy works for every agent today, including ChatGPT in a browser.
- If no answer: A ships; B stays in the backlog.

## Not verified

- The query words in `run` beyond those the reference shows (`date>18h`, `date>7d` follow the documented `date>2h`).
- That a prompt run by a real agent calls exactly these commands. The steps say what it usually runs; agents vary.
  No CLI was run against a real account.
- How the page reads with 30+ guides. Beyond about 15, a filter by tool may be needed.
