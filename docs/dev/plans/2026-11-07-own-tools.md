# Own tools: add a WireCat-compatible CLI from Desktop

Status: **built** (2026-11-07, #172; user docs #176). Builds the "Your own tools" section of [cli-registry.md](../cli-registry.md) and
replaces its hand-written `desktop` object with a manifest the CLI generates. Journal:
[2026-11-07-own-tools](../../journal/2026-11-07-own-tools.md).

## Outcome

An independent developer generates a CLI with cli-template, publishes it under their own npm scope with trusted
publishing, and a user adds it in Desktop by typing its package name. No JSON file, no environment variable. An agent
then finds its commands, MCP tools and skill the same way it finds a WireCat tool's.

## Three kinds of tool

| Kind | Source | Badge | Provenance | Rules |
|---|---|---|---|---|
| Official | `catalog/tools.json`, compiled in | none | must be WireCatLabs `release.yml` on `main` | `@wirecat/` only |
| Community | signed list `wirecat.dev/registry/v1/desktop-tools.json` | **Community** | must match the entry's repo; refuses | every `community.rs` rule |
| Own | `<app data>/extra-tools.json`, written by the app | **Not checked** | shown, never refuses | every `community.rs` rule except a repo outside GitHub may be missing |

The badge comes from the source file, never from a key in the entry. The app reads the signed list first, then
`extra-tools.json` while the switch is on; `WIRECAT_EXTRA_TOOLS=1` turns the file on without the switch, for
developers, and no longer hides the signed list. Only scoped TypeScript packages built on cli-base are
supported: no local PATH programs, no unscoped names (owner, NEED-2280).

## The manifest (format 2)

One file, `contracts/wirecat.json`, shipped in the npm tarball. `cli-dev manifest` writes it from the built program;
`cli-dev manifest --check` fails CI when it is stale, like the other contracts. The developer writes only what code
cannot know: a tagline and the sign-in texts, once, in the CLI's identity.

```jsonc
{
  "wcat_manifest": 2,
  "name": "acme-crm", "version": "0.3.0", "description": "...", "docs_url": "https://...",
  "package": "@leemour/acme-crm-cli", "bin": "wcat-acme-crm",
  "commands": [
    { "path": ["contacts", "list"], "effects": { "remote": "read", "local": "write" }, "permission": "contacts" }
  ],
  "desktop": {                      // exactly the catalog keys community.rs checks; null when unused
    "tagline": "...", "profiles": {"args": [...], "shape": "items"}, "doctor": [...], "setup": [...],
    "signIn": {"gives": "...", "asks": "..."}, "sync": [...], "runs": [...], "skill": {...}, "mcpServer": [...],
    "storage": {"app": "leemour-acme-crm-cli", "env": "ACME_CRM"}
  }
}
```

- **Derived, not declared:** `commands` from the command tree (`describeProgram` with `effects` and permission keys),
  `doctor`/`sync`/`runs`/`mcpServer`/`profiles` from the presence of the standard commands and their standard words,
  `skill` from `skills/`, `storage` from the identity's app name and env prefix.
- **No command line from the package is ever run during discovery.** Desktop reads the file as text out of the
  tarball, checks the tarball against npm's `dist.integrity`, and validates every array with the `community.rs`
  word rule. The words are run later, without a shell, only after both confirmations.
- **`--wcat-describe` format 2** prints the format-1 keys with `"wcat_describe": 2`, plus `desktop` and
  `manifest_sha256` of the shipped file. It reads the file instead of rebuilding it, so the two cannot differ. The
  command list stays out of it to keep the answer under the umbrella's 64 KiB cap. Format 1 readers ignore the new keys.
- **After install** Desktop runs `--wcat-describe` once, inside the second confirmation, and refuses the tool when
  `manifest_sha256` differs from the file it showed.
- **No manifest** (a format-1 CLI or none): Desktop says the tool does not describe itself, and offers the manual
  fallback the registry plan names: paste the `desktop` object, checked by the same rules. It never guesses words.
- **What a manifest proves:** what the CLI *declares*. cli-core enforces declared `effects` against permission levels
  at run time; provenance ties the tarball to a public commit. Nothing proves that arbitrary code does only what it
  declares, so the interface says "asks for", never "can only".

**Data folder of an own tool.** Deleting a tool's data removes only folders whose last part is its `storage.app`
(`storage.rs`, `ensure_ours`); `storage.env` only names variables that can move those folders, and a moved folder
must still end in `storage.app`. So the folder name is what must belong to the tool. For an own tool from
`@<scope>/<name>`, `storage.app` lower-cased must be `<scope>-<name>` or start with `<scope>-<name>-`, with every
`.` and `_` of the package name turned into `-` (`@leemour/acme-crm-cli` → `leemour-acme-crm-cli`, `@x/a_b` →
`x-a-b`), at most 64 characters. An own tool's folders are always its default locations: a `<PREFIX>_CONFIG_DIR`
override does not move what Delete data removes. A folder that already existed when the owner added the tool is
recorded in its entry (`own.preexisting`, kept by updates); Delete data lists it with why it stays and never removes
it, because a free scope can still match another program's folder (`@google/chrome` → `google-chrome`). Only the scope's owner can publish under
a scope, so that folder name is theirs; the unscoped name alone (`@evil/gh` → `gh`) and the manifest's own `name`
prove nothing. `storage.env` has no naming rule, but it may not be one an official tool or the shared store uses. A
manifest that breaks the rule is refused as `bad_manifest(storage)`, at review and at every start.

## Desktop flow

1. **Settings switch** "Allow tools WireCat has not checked", off by default, with the warning from cli-registry.md
   §1. While on, the Tools page shows **Add your own tool** at the top, next to Check again (NEED-2281).
2. **Package name.** Scoped name only, checked before any network call.
3. **Discovery, no install:** `npm view <pkg> --json` (version, `repository`, `dist.integrity`, `dist.tarball`,
   maintainers), the attestation as `provenance.rs` already reads it, and the tarball's `contracts/wirecat.json`.
   Bounded: HTTPS, 20 s, 512 KB packument, 10 MB tarball, the manifest file at most 256 KB.
4. **The review screen** shows publisher (npm maintainers), repository, version, provenance ("Built by
   `<repo>` on GitHub Actions" or "No record of where npm built it"), the requested access grouped as *reads your
   service / changes your service / writes on this computer*, sign-in, sync, agent connection, and the warning that
   WireCat has not reviewed it. A failed check shows its reason in a sentence and what to do (§ Failures).
5. **First confirmation:** Add. **Second confirmation:** "Install and run `<pkg>`? Its install scripts and first run
   use your permissions." Only that button installs, because npm's install scripts are the package's first run.
6. **Install** through `install.rs`; `confirm_release` *reports* provenance for own tools instead of refusing, and
   refuses when the attestation names a different repository than the review screen showed.
7. **Verify** with `--wcat-describe` (hash match), save the entry to `extra-tools.json`, restart prompt, and the tool
   appears in the Tools list with **Not checked**.
8. **Use:** sign-in, sync, doctor, logs, skill and MCP connection work from the entry's words like any tool.
9. **Update:** every Install or Update of an own tool, from any button, opens this review for the new version
   (`install` in `src/shared/tools-store.ts`); Choose tools in the setup does not list own tools. The review shows
   what changed; any change, or access the tool does not describe, needs "I accept these changes" before Update.
10. **Remove from WireCat** deletes the entry and offers Uninstall; deleting data offers only the folders named by its
    own `storage`, never the shared store (`ensure_ours`), and never a folder that existed when the tool was added
    (`own.preexisting`).

Discovery and review live in a new Rust module `own_tools.rs` with commands in `commands/own_tools.rs`; the UI is
`OwnToolDialog.tsx`, `AddOwnTool.tsx`, `RemoveOwn.tsx` and `messages-own.tsx` in `src/features/tools/`, with the
dialog's store in `src/shared/own-dialog-store.ts`. Both reuse `community.rs` validation and `provenance.rs` reading.

## Failures the user can act on

Every refusal is a kind plus a sentence, shown in the dialog and on the Tools row, never only in the console:
`not_found`, `not_scoped`, `wirecat_scope`, `no_manifest` (→ manual fallback), `bad_manifest` (which key, which rule),
`collision` (which official or listed tool owns the name; "Remove your own entry to use the listed one"),
`provenance_mismatch`, `offline`, `too_large`. Any other error shows as "Something went wrong reading npm:
`<message>`". The signed list's refusals get the same treatment in Settings.

## Developer side

- **cli-base:** `cli-dev manifest`, the format-2 answer in `wcatStart`, identity fields `tagline` and `signIn`, the
  `manifest` contract in [WC-CMD-29](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/commands.md),
  and `new-cli.md` updated.
- **cli-template:** the generated bin calls `wcatStart`; generated `files` ships `contracts/`; `pnpm generate` writes
  the manifest; provider kinds come from cli-core's list (adds `crm`), and the docs stop assuming a message source.
- **cli-core:** `readonly` refuses a command with undeclared effects (SEC-116), so a forgotten declaration fails closed.
- **Example:** `leemour/acme-crm-cli`, published as `@leemour/acme-crm-cli` with trusted publishing: a fake CRM
  service served from local fixtures with a synthetic token, contacts and deals through cli-core's `./crm` port
  (`CrmSource`, `syncCrm`), invoices through the records envelope (`ingest`). No SQL of its own.

## Acceptance

Rust and Vitest cover each failure kind, collision with an official and a listed tool, both confirmations, offline
discovery and offline use, update with changed provenance, and removal that leaves the shared store. One manual run on
a release build: Add `@leemour/acme-crm-cli` → install → sign in with the synthetic token → sync → connect Claude Code
→ the agent answers a question from the synthetic deals.
