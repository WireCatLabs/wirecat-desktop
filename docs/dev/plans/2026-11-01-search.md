# Search: results by kind, what surrounds a result, and a query from plain words

Owner's review, 2026-11-01: "think about how we can find the context around a message, mb find nearest messages by a
button or read full transcript or get links to files etc. and think better how search would work for different types
eg meetings, email and so on", and "add a field above search to generate a query using AI - ask an agent - say
claude/codex or use api key to generate query from the request".

Rule 1 holds throughout: every action runs the tool's own command from a catalog template (`search.context` in
`catalog/tools.json`); the app parses nothing the tool did not print, and a capability the tool lacks is listed
under "Gaps" for its CLI, not built here.

## Results by kind

| Kind | Tools | A row shows | Its details offer | Command behind it |
| --- | --- | --- | --- | --- |
| Messages | tg, max, wa | when, chat, sender, excerpt | Show messages around it (5 before, 5 after, the hit marked; attached files by name) | `<tool> <profile> messages context <ref> --before-n 5 --after-n 5 --offline --no-record --json` |
| Mail | email (memo) | when, subject, sender, excerpt | Show the thread (5 earlier, 5 later mails of the thread) | `memo messages show <ref> --before-n 5 --after-n 5 --no-record --json` |
| Meetings | zm | when, meeting title, excerpt | Read the transcript (every line, speaker and time; the line the hit was found in marked and centred) | `zm <profile> meetings transcript <meeting id> --no-record --json`, the id read from the hit's ref |
| Documents | drive | when changed, title, excerpt | Open the original (the hit's https `url`) | none: the hit carries the link |
| Notes | memo | when changed, title, excerpt | none yet (see gaps) | `memo notes show <ref> --json` exists, not wired |

Every value in a result's details can filter the search (adds `field:value` and searches again), exclude it, group the
shown page by it, or be copied, as in Logs. Only values with a field in the tool's query language filter: `chat`,
`from`, `label`, `title`, `tag` (`hitField` in `src/domain/search.ts`).

## Gaps in the CLIs

Each is a CLI change, in the repo named; the app adds nothing in its place.

1. **A message hit names no attachments** (cli-core). `has:` filters by them, but the hit JSON has no `attachments`;
   only `messages context` / `show` list them. A search hit could carry `attachments[]{kind,name,size}`.
2. **No file download from the local store by ref** (cli-core). `messages download` takes chat and id, not a `msg:` ref,
   and fetches over the network, which this page never does. Wanted: `messages download <ref> --offline` for files the
   store already has, printing the saved path.
3. **No link to a file** (cli-core). `messages link <ref>` gives the message's link (sometimes null), not the file's.
4. **zm: no command opens a hit's place** (zoom-cli). `search all` hits are `meeting:<account>/<meeting>`, which
   `meetings passage` rejects, and carry `offset_ms` but no speaker. Wanted: `meetings passage <hit ref> --at <ms>
   --before-n 3 --after-n 3`, or a cue ref in the hit.
5. **Mail attachments: text only** (cli-memo). No command lists or saves an attachment file; mail synced by `mail`
   has none at all.
6. **drive: `documents show` does not take the hit ref** (drive-cli); only a Google id or Docs URL.
7. **No plain-words-to-query command anywhere** (cli-core). See the next section.

## A query from plain words

Above the query box: "Describe what you're looking for", a field and "Write the query". The written query goes into
the box for the owner to check and change; nothing is searched until he presses Search, so the tool's own query check
marks any mistake in the usual way. Built in the browser build only (`?search-ai=` below); the app hides the field
until the command exists.

**Who writes it**, in the order the owner chose (NEED-210/211/212 = A; the options and their measurements are in
`docs/dev/research/2026-11-01-fact-extraction-options.md`):

1. The owner's own signed-in Claude Code: `claude -p --model haiku --tools "" --strict-mcp-config --setting-sources ""
   --no-session-persistence --output-format json --json-schema <{query}> --system-prompt <the tool's query language>`,
   the request on stdin.
2. Sign in with ChatGPT, the owner's plan (to be tested first).
3. Codex CLI, signed in, with the warning that it can see files on this computer.
4. The owner's own API key.

**What leaves the computer**: the owner's words and the tool's query language (fields, operators, examples). Never a
message, a hit or a chat name from the store.

**Where it lives** (rule 1): a cli-core command every tool gets, `<tool> search --explain "<request>" --writer
claude-code|chatgpt|codex|key --json`, answering `{query, writer}` or a closed reason (`writer.none`,
`writer.signed-out`, `writer.limit`, `writer.failed`). It shares the reader providers memo gets for suggested facts, so
there is one provider layer, in cli-core. The app adds one catalog template (`search.explain`) and one Tauri command,
like `search_context`.

**Estimate**: cli-core command and the Claude Code provider, with tests on made-up requests: 1.5 days. The other three
providers ride on the fact-extraction work. App wiring (template, command, real errors): half a day.

**States** (browser build): works (`?search=tg`), Codex writes it with its warning (`?search-ai=codex`), nothing set up
(`?search-ai=none`: the four ways, and "type the query yourself meanwhile"), the writer fails (`?search-ai=fail`), an
empty request (press Write the query with nothing typed).

## Not verified

- The real output of `messages context`, `memo messages show` and `meetings transcript` was read from the CLIs' source
  and docs, not run: the mock follows that shape.
- Whether `--offline` and `--no-record` are accepted after `messages context` and `meetings transcript`. A tool that
  refuses an option shows "too old, update it", which would mislead here.
- Whether the meeting id in a `search all` hit's ref is the stored id `meetings transcript` takes.
